# 第14篇：UDP NAT —— 给"无连接"的协议建连接

## 一

TCP 像一个凡事都要签字的德国官僚。三次握手签到，四次挥手签退，中间每个数据包都有编号，到了要确认，没到要重发。给 TCP 做 NAT 是簿记——有头有尾，记录完整。

UDP 像一个把纸条揉成团扔进你家窗户就跑的小孩。纸条上写着"给我 www.google.com 的 IP 地址"（这是一个 DNS 查询）。你写好答案揉成团扔回去。全程没有握手、没有重传、没有再见。给 UDP 做 NAT 是侦探工作——你得自己推断什么时候开始、什么时候结束。

## 二

UDP NAT 面临两个独有的难题。

**难题一：什么时候开始？** TCP 有 SYN 标志——NAT 看到了就知道"新连接来了"。UDP 没有——第一个数据报看起来跟第二百个一模一样。怎么知道该创建映射了？答案：**看到任何新的四元组就创建。** 不需要等什么标志，因为根本没有标志。

**难题二：什么时候结束？** TCP 有 FIN，"这个连接完了"。UDP 没有——客户端查完 DNS 就忘了这件事。NAT 什么时候可以安全删除映射？答案：**超时没活动就删。** 我们设了 180 秒——大多数 UDP 应用（DNS 通常几秒内完成，WebRTC 和游戏有持续数据流）都覆盖到了。偶尔有心跳间隔超过 180 秒的 IoT 设备——对它们来说每次心跳都被当作新会话。这不太优雅，但对于家庭网络场景，够用。

## 三

UDP NAT 的核心机制是**虚拟端口池**。因为同一个内网 IP:Port 可能向不同目标发数据报，不能像 TCP 那样直接用 IP+Port 做唯一标识。需要为每个 UDP 会话分配一个唯一的虚拟端口，响应包到达时通过虚拟端口反查原始客户端。

虚拟端口从 5000 到 65000——60000 个端口。家庭网络顶多同时几百个 UDP 会话，绝对够用。分配时从队列头取一个，回收时放回队列尾。端口映射表 `m_vport_to_udp` 用 `unordered_map` 存储——`vport → {原始四元组, 最后活跃时间}`。

响应路由是 UDP 代理最精妙的逻辑：SOCKS5 代理的 UDP 响应回来时，目标端口是我们的虚拟端口。查 `vport_to_udp` → 拿到原始四元组 → 知道"这个响应是给哪个客户端的哪个端口的" → 转发。

## 四

UDP 校验和在 NAT 环境下有一个容易被忽略的细节。IP 层校验和只校验 IP 头，UDP 的校验和校验的是"UDP 头 + 数据 + 伪头部"。伪头部包含了源 IP 和目标 IP。NAT 修改了 IP 头的源地址——如果不重新计算 UDP 校验和，客户端收到后校验失败，**静默丢弃**。你不会看到错误日志，只是客户端一直在等响应。

代码里有一个微优化叫增量校验和更新（incremental update）：如果你只修改了 IP 地址，不需要遍历整个数据报重算校验和——只需在旧校验和里减去旧地址的贡献，加上新地址的贡献。几十个 CPU 周期的事，不值得从头算一遍。

## 五

UDP 代理的复杂度不在于"怎么做"，而在于"边界条件怎么处理"。超时取多少秒？虚拟端口耗光了怎么办？校验和不重新算会被丢包吗？这些问题课本上不会写，只能写了代码跑起来看。
