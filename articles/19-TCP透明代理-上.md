# 第19篇：TCP 透明代理 —— 拦截、重定向与桥接

## 一

一个 TCP SYN 包到达 NDIS worker 的处理循环时，整个透明代理的流程就启动了。这是判决时刻——直连、代理、还是阻断？而判决所需的几乎所有信息，都在这个包和紧随其后的几个包里。

## 二

Worker 线程识别出 TCP SYN 后，走以下流程。

**提取五元组。** 源 IP、源端口、目标 IP、目标端口、协议。这五个数字是这个连接的身份证。

**创建 NAT 映射。** `NatManager::create_tcp_mapping(key, OriginalDestination(目标IP, 目标端口, 客户端IP, worker_id))`。这条映射的意义是："连接 key 原本是要去 目标IP:目标端口 的。记下来，一会儿 AppListener 要查。"

**路由决策。** 目标 IP 是中国的吗？目标域名（如果能嗅探到的话）是什么类别？RuleManager 先问，GeoChecker 补充。结果：DIRECT / PROXY / BLOCK。

**重定向。** 如果决定走 PROXY——修改包的 IP 头和 TCP 头，把目标地址改成 `127.0.0.1:3080`（AppListener 的监听地址）。重新计算校验和。然后通过 `send_to_mstcp` 把这个修改过的包注入回网络栈——Windows 以为这个包是"从网线正常到达的，目标是本机的 3080 端口"。

Windows 协议栈正常完成三次握手。手机以为自己在跟 Google 握手，实际在跟本机的 3080 端口握手。

## 三

AppListener 的 `accept()` 返回一个新的 socket——这就是"连接 A"的本地端点。AppListener 需要知道这个连接的真正目标是谁。

它从 socket 拿到客户端 IP 和端口，计算 NAT key → 查 NatManager → 拿到 `OriginalDestination(142.250.80.46, 443, ...)`。这就是手机真正想去的地方。

然后创建 `ProxyTCP` 对象，传入客户端 socket 和目标地址。ProxyTCP 的 `start()` 方法立即开始建立"连接 B"。

## 四

"连接 B" 是通过 SOCKS5 建立的。SOCKS5 协议非常简单——两步走。第一步握手协商（"我支持无认证"→"好的，用无认证"），第二步 CONNECT 命令（"帮我连到 google.com:443"→"连上了"）。

但 CONNECT 命令有一个选择：用域名格式还是 IP 格式？如果有域名——最好用域名格式，让 SOCKS5 代理服务器做 DNS 解析，避开本地 DNS 污染。如果只有 IP——只能用 IP 格式。

域名嗅探就在这个节点发挥作用。在 SOCKS5 握手完成之前，客户端可能已经发来了第一批数据——如果这批数据刚好包含 TLS ClientHello，就可以从 SNI 扩展里提取域名。如果运气更好——是明文 HTTP——可以从 Host 头里提取。两样都没有→退化为 IP 路由。

## 五

SOCKS5 连接建立后，`ProxyTCP` 进入 ESTABLISHED 状态。此时连接 A（手机↔3080）和连接 B（wifi2socks↔Google via SOCKS5）都处于就绪状态。

程序的唯一工作变成：**从 A 读到数据 → 写到 B；从 B 读到数据 → 写到 A。** 就像两个水槽之间的连通管——这边水位高了往那边流，那边水位高了往这边流。

这里有一个容易犯的错：如果目标端口是"server-first"类型的——服务器先说话（比如 SSH，连上后服务器先发版本字符串）——而你还在等客户端先发数据来触发转发，那就死锁了。客户端在等服务器说话，服务器在等客户端说话。解决方法是硬编码一个"eager ports"列表（`{22, 8022, 3306, 63306}`），这些端口不等客户端数据，直接建好代理连接就开始转发。这样服务器的"先说话"包能立刻到达客户端。
