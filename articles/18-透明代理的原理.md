# 第18篇：透明代理 —— 偷天换日

## 一

透明代理的"透明"是一个欺骗性很强的词。它不是说代理不存在——它切切实实跑在你的 CPU 上，占着内存，处理着每一个包。它说的是：**用户不知道它的存在。**

这就像一个顶级的管家。你早上起床，房间是暖的，咖啡是热的，报纸是熨过的。你完全不知道管家几点起的、干了多少活。你只需要享受结果。

透明代理就是这样的管家。你在手机上打开浏览器，输入 `www.google.com`，0.3 秒后页面出现。你不知道的是——你发出的 TCP SYN 包在离开 WiFi 芯片之后、到达 Windows 协议栈之前，被一个 NDIS 驱动截获了。这个包被送到了用户态，程序查了 NAT 表、查了规则引擎、查了 GeoIP，然后决定：走代理。程序把这个包**重定向到了一个本地端口**，从 NAT 缓存里查出真正的目标地址，发起了一次全新的 TCP 连接——通过 SOCKS5 隧道连到了真正的 Google 服务器。然后程序在两条 TCP 连接之间做数据中转。

整个过程你完全不知道。这就是"透明"。

## 二

透明代理跟显式代理的本质区别在哪？

显式代理：你需要手动配。在浏览器的网络设置里填 `127.0.0.1:1080`，或者填一个 PAC 文件 URL。你知道你在用代理。如果代理挂了，你会看到"无法连接到代理服务器"的错误。

透明代理：你不需要配任何东西。连上 WiFi 就行。你完全不知道代理存在。如果代理挂了——在你的视角就是"网断了"，你不会看到任何跟"代理"两个字的错误信息。这就是透明代理牛逼的地方，也是让人想砸键盘的地方——因为用户不知道代理存在，出了问题也不知道往哪排查。

## 三

透明代理有多种实现思路，但本质上都是做同一件事：**在不修改客户端的情况下，改变流量的目的地。**

Linux 上的经典方案是 TPROXY 和 REDIRECT。TPROXY 最优雅——内核帮你把流量重定向到本地 socket，同时保留原始目标地址信息。REDIRECT（或 DNAT）老一些——用 iptables 把目标 IP:Port 改成 127.0.0.1:本地端口，然后用 `getsockopt(SO_ORIGINAL_DST)` 拿回原始目标。

Windows 上呢？没有 TPROXY，没有 iptables。你得自己做这一切。

我们的方案：**NDIS 层拦截 + 重定向到本地端口 + NAT 缓存查原始目标 + 新建 TCP 连接 + 数据桥接。**

## 四

整个透明代理最关键的一步——也是我之前理解有误、后来在代码中纠正的一步——是连接的处理方式。

手机发出 TCP SYN → WinPkFilter 在 NDIS 层拦截 → 程序修改包的目标地址，把它**重定向到 127.0.0.1:3080**（AppListener 监听的本地端口）→ Windows 协议栈看到这个包的目标是本地 → 正常完成三次握手。

AppListener 收到这个连接。但它需要知道"这个连接原本是要去哪里的"。答案在 NAT 缓存里。在拦截 SYN 的时候，NAT 管理器已经创建了一条映射：`key(客户端IP, 客户端端口) → OriginalDestination(真实目标IP, 真实目标端口)`。AppListener 通过这条映射拿到真实目标。

然后程序**发起一次全新的 TCP 连接**——通过 SOCKS5 代理连到真实目标。这跟手机发出的原始连接是**完全独立**的。它有自己的三次握手、自己的序列号空间、自己的拥塞窗口。

现在你有两个 TCP 连接：
- **连接 A**：手机 ↔ wifi2socks（手机以为自己连的是 Google）
- **连接 B**：wifi2socks ↔ Google（真实的连接，可能经过 SOCKS5）

程序的工作是——在 A 和 B 之间桥接数据。A 收到的数据转发到 B，B 收到的数据转发给 A。

**关键**：连接 A 和连接 B 是两次**独立的、完整的** TCP 连接。各自的超时重传、ACK/SEQ 管理、拥塞窗口、快速重传——全由操作系统内核维护。程序只需要在应用层做数据转发。不需要自己实现 TCP 状态机。不需要管理超时重传。不需要操心滑动窗口。这些东西是 TCP 协议最复杂的部分——而它们都被操作系统免费提供了。

你付出的代价是：多了一次 TCP 连接的开销（但连接池可以大幅摊销），以及多了一次数据拷贝（从 A 的缓冲区拷到 B 的发送缓冲区）。跟"自己维护 TCP 状态机"比，这简直是白送。

这就是"重定向到本地端口"方案的精髓——**让操作系统干它最擅长的事（TCP 状态管理），你只干你必须干的事（路由决策和数据转发）。**

## 五

为什么不用"伪造三次握手"？

理论上可以。你拦截 SYN，自己生成 ISN，构造 SYN-ACK 发回去，手机收到后回复 ACK——三次握手完成。然后在你的程序内部，维护一个 TCP 状态机，管理序列号、ACK、窗口、重传定时器。

理论上可行。实际上这是噩梦。TCP 状态机的正确实现需要几千行经过数十年验证的代码——这正是操作系统内核的 TCP 栈。你为什么要重写一遍？在应用层模拟 TCP 状态机，性能差、bug 多、而且毫无必要——既然操作系统已经免费提供了两个完全正确的 TCP 连接，你只需要把它们的应用层数据桥接起来就够了。

这就像你有一辆法拉利和一辆兰博基尼。你要从 A 点到 B 点运货。有人建议你：自己造一辆车。更好的做法是：把两辆车都开起来，货物在 A 车卸货的地方直接装到 B 车上。
