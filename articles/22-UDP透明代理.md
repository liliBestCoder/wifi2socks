# 第22篇：UDP 透明代理 —— "无连接"才是最难的连接

## 一

TCP 代理虽然复杂，但它有一个根本优势：有状态。SYN 开始，FIN 结束，中间数据按序到达。UDP 代理什么都没有——没有连接语义、没有可靠传输、没有流量控制。第一个数据报和第两百个看起来一模一样。

但好消息是：99% 的 UDP 流量是 DNS 查询。一个请求、一个响应、一个会话结束。复杂度比看起来低很多。坏消息是：那 1%——QUIC、WebRTC、游戏数据——真的难处理。

## 二

UDP 代理的入口是 `UdpProxy::handle_client_data()`。DNS（目标端口 53）走特殊处理——优先 DNS 缓存，未命中再真正查。非 DNS 流量走通用路径：构建四元组 → 路由决策 → 如果是代理，通过 SOCKS5 UDP ASSOCIATE 转发。

SOCKS5 的 UDP 代理有个别扭的设计：你必须先建立一个 TCP 控制连接来协商 UDP ASSOCIATE，然后真正的 UDP 数据通过独立的 UDP socket 发送。TCP 控制连接断开时——UDP 中继也失效。程序得同时管理 TCP 控制连接和 UDP 数据流。

## 三

响应路由是 UDP 代理最精妙的逻辑。SOCKS5 代理回包的目标端口是虚拟端口。查 `m_vport_to_udp` 表 → 拿到原始四元组 → 知道该转发给哪个客户端。查不到 → 静默丢弃。这个静默丢弃不是因为不关心——是 UDP 没有"错误通知"机制，你除了丢没有别的选择。

## 四

QUIC 和 HTTP/3 是 UDP 的未来。越来越多的流量跑在 QUIC 上。QUIC Initial 包包含 TLS ClientHello——里面有 SNI 域名。如果能解析 QUIC 的 SNI，就能对 QUIC 流量做跟 TCP 一样的域名嗅探。目前我们的代码还没实现——Roadmap 上排着。

## 五
