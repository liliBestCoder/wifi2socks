# 第23篇：DNS 的三重奏 —— 缓存、分流与反污染

## 一

DNS 是互联网的电话本。你控制了电话本，就控制了所有人能找到谁。在中国上网，DNS 污染是家常便饭——运营商抢在真正的 DNS 服务器之前回复一个假的 IP。你的浏览器连到那个假 IP，要么打不开，要么被"温馨提示"。

做软路由，DNS 必须自己掌控。怎么掌控？三招：缓存（查过的别重复查）、分流（国内的直接查、国外的走代理查）、反污染（UDP 被干扰了走 TCP）。

## 二

DNS 缓存是系统里最简单的模块——一个 `unordered_map` + 一个读写锁。域名做 key，value 是 IP + 过期时间。TTL 在 60-600 秒之间做了裁剪——太短强制提到 60（降低缓存抖动），太长强制降到 600（避免目标 IP 变更期间缓存不更新）。缓存命中时不发任何网络请求，O(1) 哈希查找，微秒级。

## 三

分流策略简单清晰：国内域名→直连 `223.5.5.5`（阿里公共 DNS，国内解析快）；国外域名→通过代理查 `8.8.8.8`（Google DNS，不走代理容易被污染）。判断"国内还是国外"用的是 GeoSite 的 `geosite:cn` 类别——比手工维护域名列表靠谱一个数量级。

## 四

所有出站 DNS 查询——UDP 端口 53——在 NDIS 层就被拦截。不管设备配置的是什么 DNS 服务器地址，实际查询都被我们的代码接管。查缓存 → 命中直接返回；没命中 → 分流判断 → 发起真正的 DNS 查询 → 拿到结果 → 缓存 → 返回给设备。设备完全不知道被劫持了。

DNS over TCP 是当 UDP 不够用时的后备方案。UDP 响应最多 512 字节——DNSSEC、大型 TXT 记录、长 CNAME 链都会超出。超出时 DNS 服务器会设 TC（Truncation）标志位。收到 TC → 走 TCP 重试。DNS over TCP 的格式也很简单——在 DNS 消息前面加 2 字节长度字段。通过 SOCKS5 代理走的 TCP 查询天然防污染——代理连接是加密的，中间人改不了。

## 五

DNS Probe（`DnsProbeTracker`）是最"八卦"的模块。它通过 DNS 查询的域名推断设备上跑的是什么应用——`connectivitycheck.gstatic.com`→Android 联网检测，`captive.apple.com`→Apple Captive Portal，`conn-service-cn-04.allawntech.com`→OPPO 服务。这些分类的用途：联网检测流量直连放行（否则设备会误判"WiFi 需要登录"弹 Portal），厂商推送服务走代理（国内的推送在国内快，国外的推送走代理才稳定）。
