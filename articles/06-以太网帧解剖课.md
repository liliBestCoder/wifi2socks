# 第6篇：以太网帧解剖课 —— 从 MAC 地址到 TCP 端口

## 一

网络教材讲协议栈的方式通常是画画——从上往下画七层，再给每层涂不同颜色。你看完知道了协议长什么样，但不知道在代码里怎么用。

我今天换个方式。直接拿代码里实际用的手法来讲——你读完这一篇，不仅能看懂一个 TCP SYN 包的每一个字段，还能自己用三行 C++ 把它解析出来。

## 二

以太网帧是网络世界的基本粒子。不管你是在刷视频、打游戏、还是做 DNS 查询，所有数据在网线上都以以太网帧的形式存在。一个帧的开头永远是 14 字节的"信封"：

```
Byte 0-5:   目标 MAC（DMAC）—— 寄给谁
Byte 6-11:  源 MAC（SMAC）—— 谁寄的
Byte 12-13: EtherType —— 信封里装的什么
```

如果目标 MAC 是 `ff:ff:ff:ff:ff:ff`，就是广播——"所有人注意！"。ARP 请求用它，DHCP DISCOVER 也用它。如果你的 MAC 地址恰好跟目标 MAC 匹配（或者你开着混杂模式），网卡就把帧收上来交给驱动。

EtherType 只有两个字节，但决定了怎么处理后面的一切。`0x0800` = IPv4（请按 IP 头解析）；`0x0806` = ARP；`0x86DD` = IPv6。如果你漏掉了 IPv6 的判断——比如只检查 `0x0800`——那所有 IPv6 流量都会被当成"不明物体"跳过。这就是为什么代码里有一个 `m_stat_ipv6_drop` 计数器——不是没看到，是看到了暂时不处理。

## 三

EtherType = 0x0800 时，以太网帧的 payload 是一个 IPv4 包。IP 头标准长度 20 字节，每个字段各司其职：

**Ver_HLen**：一个字节干了两个人的活。高 4 位是版本号（4 = IPv4），低 4 位是头长度（以 4 字节为单位）。取头长度写 `(Ver_HLen & 0x0F) * 4`。

**Len**：IP 包总长度。这个字段的上限是 65535，但实际上超过 MTU 的包会被分片。

**Flags_Frag**：高 3 位是标志位。其中 Don't Fragment（DF）标志最重要——如果 DF=1，这个包不能被分片。经过一个 MTU 不够的路由器时，它会被丢弃并返回 ICMP "需要分片"。这就是 Path MTU Discovery 的底层机制。

**TTL**：每过一个路由器减 1，减到 0 包就被丢。初始值常见 64 或 128。它的存在是为了防止路由成环——如果没有 TTL，一个陷入死循环的包会在互联网上永远流浪，像一个找不到家的幽灵。

**Proto**：上层协议类型。6 = TCP，17 = UDP，1 = ICMP。这个一字节决定了 IP payload 应该交给谁解析。

解析 IP 头的时候有一个常见 bug：**IP 头不一定 20 字节。** 如果有 IP 选项（很少见但不是没有），头会更长。所以必须从 `Ver_HLen` 里取出实际长度，不能硬编码 `ip + 20`。

## 四

IP Proto = 6 时，接着的是 TCP 头。TCP 头的精巧程度在整个互联网协议族里数一数二。

**端口号**：源端口和目标端口各 16 位（0-65535）。端口 0-1023 是"著名端口"（well-known ports）——80=HTTP、443=HTTPS、22=SSH。端口不是你随便选的，但你可以偶尔任性一下。

**序列号与确认号**：这两个 32 位数字是 TCP 的灵魂。序列号告诉对方"我发的数据从哪里开始"，确认号告诉对方"你发的数据我收到了多少"。它们是 TCP 可靠传输的基础。

**Flags（标志位）**：8 个 bit，每个都是独立开关。SYN=0x02（"我们建立连接吧"），ACK=0x10（"我收到了"），FIN=0x01（"我要走了"），RST=0x04（"出错了，重来"）。在透明代理里，一个 SYN 包到达的那一刻，就是整个路由决策流程启动的时刻。

**窗口大小**：告诉对方"我还能收多少数据"。这是 TCP 流量控制的基础。窗口为零的意思是"你先别发，我处理不过来了"。

**HdrLen**：TCP 头也不一定 20 字节。有 TCP 选项（比如 MSS、窗口缩放、时间戳）时会更长。跟 IP 头一样，从高 4 位取长度。

## 五

IP Proto = 17 时，接着的是 UDP 头——只有 8 字节。源端口、目标端口、长度、校验和。就四样。

UDP 的设计哲学是"我尽量简单，剩下的你看着办"。没有序列号就没有可靠传输，没有窗口就没有流量控制，没有 SYN/FIN 就没有连接概念。UDP 就是一个加了端口号的 IP 包。

但在 DNS（端口 53）的场景里，UDP 的简单反而是优势。一个 DNS 查询只需要几十字节，放在一个 UDP 数据报里发出去，对方回一个一两百字节的响应。整个过程一次往返，不需要三次握手、不需要四次挥手。轻巧到极致。

## 六

ICMP 头用于诊断。最常见的是 ping——Type=8 Echo Request，对方回 Type=0 Echo Reply。在软路由里，客户端偶尔会 ping 网关来测试连通性。我们的处理方式是：收到 Echo Request，交换源 IP 和目标 IP，改成 Echo Reply，重新算校验和，发回去。如果这个逻辑写错了——比如校验和没重新算——客户端收到的 Reply 校验失败，静默丢弃。用户看到的不是"网关回了"，而是"ping 不通"。而你不知道为什么 ping 不通，因为你的程序根本没报错。

## 七

ARP 是另一种动物。它的 EtherType 是 0x0806，不是 0x0800。它的 payload 不是 IP 包，而是 28 字节的 ARP 载荷。ARP 的 OpCode 只有两个值：1=Request（"谁的 IP 是 xxx？"），2=Reply（"我是！我的 MAC 是 xxx。"）。

ARP 最让人不安的地方是——**任何人都可以回答。** 没有认证机制，没有校验机制。任何设备都可以抢在正确答案之前说"我是 xxx！"。这就是 ARP 欺骗的原理，也是为什么在公共 WiFi 上建议用 HTTPS——即使有人在 ARP 层劫持了你的流量，他看到的是加密的。

在我们的软路由里，ARP 被直接透传——不做任何修改。因为我们需要网关 IP 对局域网内的设备"可见"。如果有人 ARP 问"谁是 192.168.137.1？"，我们让 Windows 的网络栈自己回答。这不是偷懒——是让 Windows 处理 ARP 比我们自己写 ARP 响应靠谱得多。

## 八

解析这些协议头，代码里有一种"不合规但人人用"的技巧：指针强转。

```cpp
char* frame = ...;                              // 原始帧
IP_HEADER* ip = (IP_HEADER*)(frame + 14);      // 跳过以太网头，强转
TCP_HEADER* tcp = (TCP_HEADER*)((char*)ip + ip_hdr_len);  // 跳过IP头
```

这在 C++ 标准里属于未定义行为（严格别名规则），但 Linux 内核、FreeBSD、Windows 自身的网络栈全在这么用。因为它是最快的解析方式——没有拷贝、没有函数调用、没有循环，就是一次指针加减 + 一次解引用。现实世界的 C++ 编程，永远在"标准说了什么"和"CPU 实际怎么跑"之间取平衡。这个平衡的另一个名字叫"工程经验"。
