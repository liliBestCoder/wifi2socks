# 第7篇：ARP 的谎言与 DHCP 的魔法

## 一

ARP 是全互联网最爱说谎的协议。

它的工作原理简单到幼稚：A 想知道 B 的 MAC 地址，A 发一个广播："谁的 IP 是 192.168.1.5？告诉我你的 MAC。" B 听到后单播回复："我是！我的 MAC 是 aa:bb:cc:dd:ee:ff。" A 收到，记在 ARP 缓存里。

问题在哪？在于**任何人都可以回答**。C 也听到了广播，C 可以抢在 B 前面回复："我是 192.168.1.5！我的 MAC 是 zz:zz:zz:zz:zz:zz！" A 信了。之后 A 发给 B 的包全部发给 C。

这要是放在人类社会，相当于任何人都可以跑去银行说"我是马云"，然后柜员就把钱给他。ARP 没有身份验证、没有签名校验、没有任何防伪机制。它就是互联网世界里的一个过分天真的传话游戏。

所以公共 WiFi 不安全不是传闻——ARP 欺骗到今天依然是局域网攻击的最简单手段。好消息是 HTTPS 让攻击者即使截获了包也看不到内容。坏消息是攻击者仍然可以知道你在访问哪个网站——TLS SNI 是明文的。

在我们的软路由里，ARP 被直接透传——什么都不做，让 Windows 的网络栈自己处理。这不是偷懒，是策略：Windows 的 ARP 实现比你手动写的可靠一百倍。我们只关心一件事：网关 IP 对于 ARP 请求要可达。设备问"谁是 192.168.137.1？"，Windows 内核回答"我是！"。剩下的事我们不插手。

## 二

1993 年之前，插网线上网需要手动配 IP。你得找网管要一个没人用的 IP、子网掩码、网关 IP、DNS 服务器 IP——四样缺一不可。配错了（比如跟别人的 IP 重复了），你们俩都上不了网，没人告诉你为什么。

DHCP 的出现终结了这个噩梦。它的协议流程是一段精心编排的四步舞：

**第一步：DISCOVER。** 客户端刚插上网线（或刚连上 WiFi），不知道自己是谁。它发一个广播包——目标 IP 是 255.255.255.255，目标 MAC 是全 F——"有人在吗？我需要一个 IP！" UDP 源端口 68，目标端口 67。

**第二步：OFFER。** DHCP 服务器收到，在自己管理的地址池里找一个空闲 IP。回复（单播或广播）："我有一个 IP 可以给你：192.168.137.101。我的网关是 192.168.137.1，DNS 是 xxx。你要吗？"

**第三步：REQUEST。** 客户端可能收到多个 OFFER（如果网络上有多个 DHCP 服务器——这不是好事，说明有人在捣乱或者配置错了）。它选一个，然后广播 REQUEST："我就要 192.168.137.101 了！其他人别给了！"

**第四步：ACK。** 被选中的服务器确认："好的，192.168.137.101 是你的了。租期从现在开始。" 客户端收到 ACK，把 IP 配到网卡上。世界和平。

这四步里，客户端的身份标识是 MAC 地址（在 DHCP 包的 `chaddr` 字段里）。服务器通过 MAC 地址识别"这是谁在请求"，并且可以记住"这个 MAC 设备上次拿的是哪个 IP"——这就是 MAC 绑定。

## 三

在我们的软路由里，有线模式下必须自己运行 DHCP 服务器——因为 Windows 的 ICS（Internet Connection Sharing）在有线模式下不管 DHCP。WiFi 模式下的情况相反：**如果开启自己的 DHCP，会影响 WiFi Direct AP 的内部状态，导致 WiFi 热点自己断开。** 所以在 WiFi 模式下我们禁用内置 DHCP，让 ICS 接管。

但 ICS 的 DHCP 有一个问题：**苹果手机在 ICS 的 DHCP 下经常拿不到 DNS 服务器地址。** 症状是：iPhone 连上热点，拿到了 IP，但浏览器打不开任何网页，WiFi 设置里 DNS 一栏是空的。用户必须手动去 WiFi 设置里填 DNS 服务器地址才能上网。

这就是为什么我们的代码里有一个 `patch_dhcp_ack_dns()` 函数。它在 ICS 发出的 DHCP ACK 包里动态插入一个 DNS Option（Option 6），把 DNS 服务器写死为 `192.168.137.1`（网关 IP）。这样一来 iPhone 就不用手动配 DNS 了。

这个函数做的事情说起来简单：找到 ACK 包的 END Option（Option 255），在它之前插入 6 字节（code=6, length=4, ip=网关IP），然后更新 UDP 长度、IP 总长度、IP 校验和。每一步都不能忘——忘一步，这个 ACK 包在客户端校验失败，被静默丢弃，iPhone 连 IP 都拿不到。

而且——哪怕设备自己有内置的 DNS 服务器地址也没关系。因为我们的代码拦截了**所有出站的 UDP 53 端口的包**。不管设备试图向哪个 DNS 服务器查询，DNS 包都会被我们拦截，走内部的 DNS 解析逻辑（缓存 + 分流 + DNS over TCP），然后把结果构造好返回给设备。设备以为自己跟 `8.8.8.8` 完成了通信，实际上从头到尾没一个包离开过我们的系统。

这就是 DNS 劫持——透明代理最基础的组件之一。

## 四

DHCP 还有一个容易被忽视的设计精妙之处：Transaction ID（xid）。这是一个 32 位的随机数，客户端在 DISCOVER 里生成。服务器的 OFFER 必须带着同一个 xid 回来。客户端用 xid 匹配请求和响应——"这个 OFFER 是针对我刚才那个 DISCOVER 的，不是我三分钟前那个。"

在一个繁忙的网络上，没有 xid 的话，客户端可能收到一个卖 CD 的人回答的"你要的 IP 是 xxx"——但实际上客户端可能早就换了一个问题。xid 就像一个取号小票，保证问和答是一一对应的。
