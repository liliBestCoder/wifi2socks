# 第17篇：GeoSite —— 域名分类的瑞士军刀

## 一

GeoIP 有一个永远解决不了的问题：同一个域名的 IP 地址一直在变。

你今天在北京解析 `www.google.com`，拿到的是北京谷歌云节点的 IP。明天去上海出差，拿到的是杭州的节点。下周去新加坡——完全另一个 IP 段。

但 `www.google.com` 永远是 `www.google.com`。IP 可以变，域名这个字符串是不变的。GeoIP 回答的是"这个 IP 是哪个国家的"——答案可能今天对明天错。GeoSite 回答的是"这个域名属于哪个类别"——答案比较稳定。

这就是 GeoSite 存在的理由。它不像 GeoIP 那样依赖 IP 归属，它是域名级别的分类。

## 二

V2Ray 的 geosite.dat 也是 Protobuf 编码。解析后得到四种匹配方式的索引：

**精确匹配（exact）**：`www.google.com` 精确等于 `www.google.com`。哈希表 O(1)。

**后缀匹配（suffix）**：`google.com` 匹配 `www.google.com`、`mail.google.com`。遍历后缀表 O(N)，但后缀表不大（几百条），所以也不慢。关键是要确保 `fakegoogle.com` 不会误匹配——必须在域名边界处检查。

**关键词匹配（keyword）**：域名里包含某个子串。比后缀更宽泛但更慢——要扫描整个域名字符串。

**正则匹配（regex）**：最灵活也最慢。geosite.dat 里正则规则很少——V2Ray 的维护者也懂得正则性能差。我们的实现里正则规则被预编译成 `std::regex` 对象。

## 三

查询顺序是从快到慢逐层尝试——精确匹配 → 后缀匹配 → 关键词匹配 → 正则匹配。99% 的域名在前两层就解决了。最慢的正则几乎不会被触发——但它存在是因为那一两个特殊的域名真的需要正则才能匹配。

查询结果是一个 32 位 flags 整数。高 16 位是类别标记（FLAG_CN、FLAG_GOOGLE、FLAG_TENCENT 等），低 16 位是 geosite 代码索引。一次位运算就能同时判断多个类别。

这就像你进了一家超市，门口扫一下会员卡，系统同时告诉你：你是白金会员（flags 高位）、你在北京朝阳区（code_index）、你今天能用生鲜区的折扣（另一个 flags bit）。一次查询，多个判断。

## 四

GeoIP 和 GeoSite 不是"二选一"——它们是互补的。

路由决策的完整逻辑是：GeoSite 匹配到 cn 类别 → 直连。GeoSite 匹配到 google 类别 → 代理。如果 GeoSite 没匹配到 → GeoIP 判断 IP 是不是中国的 → 中国直连、外国代理。两者都没匹配到 → 默认走代理（宁可多走不少走）。

域名比 IP 更稳定，所以 GeoSite 优先级高于 GeoIP。这也是 V2Ray 社区多年实践的经验——"按域名分流比按 IP 分流更可靠"。

## 五

GeoSite + GeoIP + RuleManager = 三层路由防线。RuleManager 是第一道（用户的显式规则），GeoSite 是第二道（域名的社区分类），GeoIP 是第三道（IP 的地理归属）。三道防线按优先级叠加，覆盖了从"明确指定"到"自动推断"的全部场景。

分流之后呢？如果判断结果是 PROXY —— 流量就进入透明代理。下一篇——整个系列最硬核的部分——透明代理的原理与实现。
