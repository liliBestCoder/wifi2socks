# 第11篇：自己动手实现 DHCP（上）—— 协议比你想象的简单

## 一

RFC 2131——DHCP 规范——全文约 40 页。我第一次打开的时候，看到的是一堵墙：BOOTP 兼容性、Relay Agent 行为、Option 重载、租约时间协商……每个概念都像一座需要爬的山。

等我真正开始写代码，发现没那么可怕。你可以先忽略 90%，只关注 10%：**四种消息类型、一个 TLV 编码格式、UDP 端口 67/68。** 其他的——Relay Agent、DHCPv6、INFORM 消息——在家庭网络场景里根本不会出现。就像你不用为了煎一个鸡蛋而读完一整本《法国料理圣经》——知道怎么打蛋、怎么翻面就够了。

## 二

DHCP 消息跑在 UDP 上。为什么不是 TCP？因为 TCP 需要先有 IP 连接，而 DHCP 的目的就是分配 IP——先有鸡还是先有蛋的问题。所以 UDP 是正确的选择。客户端用 68 端口，服务器用 67 端口。

DHCP 数据包的内存布局，从最内层（payload）往外看：

前面 240 字节是固定字段——操作码（1=请求/2=响应）、硬件类型（1=以太网）、硬件地址长度（6=MAC）、事务 ID（xid，请求和响应必须一致）、客户端 MAC（chaddr，16 字节，以太网只用前 6）、等等。这些字段大部分你只需要"读"或者"照抄"，不需要深入理解每一个。

然后 4 字节魔法数字：`0x63 0x82 0x53 0x63`。这不是随便选的——它是 DHCP 协议规定的标记，用来分隔固定字段和 Option 区域。在代码里，`handle_request_buffer()` 第一步就是验证这个魔法数字。对不上？说明这个包不是 DHCP（可能是 BOOTP 或者其他古老协议），直接返回。

之后就是 Option 区域：TLV 编码（Type-Length-Value）。每个 Option 三个部分组成——1 字节类型码、1 字节长度、N 字节值。

## 三

关键的 Option 就那几个：

**Option 53**（DHCP Message Type）：1=DISCOVER, 2=OFFER, 3=REQUEST, 5=ACK。它是 DHCP 服务器判断"客户端在干嘛"的第一依据。

**Option 50**（Requested IP）：客户端在 REQUEST 阶段说"我想要这个 IP"。

**Option 54**（Server Identifier）：告诉客户端"是哪个服务器在跟你说话"。当网络上有多台 DHCP 服务器时（这是一种常见配置错误），客户端用这个 Option 区分。

**Option 51**（IP Lease Time）：租约时长，单位秒。客户端在这个时间的一半时会尝试续租。如果服务器没回应，在 87.5% 时间再次尝试。

**Option 1/3/6**：子网掩码、默认网关、DNS 服务器——这三个 Option 合在一起就是"客户端上网需要的全部配置"。

解析 Option 的循环很简单：从位置 240 开始，读一个字节 → 判断是 padding(0)、END(255)、还是正常 Option → 读出长度 → 处理 → 偏移跳过。**唯一必须做的安全检查**：每次循环迭代都要确认 `pos + 2 + len` 没有超出缓冲区。不检查的话，一个损坏的 DHCP 包能让你的程序读到未分配内存然后崩溃。

## 四

四步握手——DISCOVER → OFFER → REQUEST → ACK——每一步都很直白。

客户端 DISCOVER 里没有 Requested IP（它还不知道有哪些可用的）。OFFER 里服务器填上 `yiaddr`（"你的 IP"）和 Option 54（"是我给的"）。

客户端收到 OFFER，等几毫秒（看有没有其他服务器也给了 OFFER），然后广播 REQUEST——包含 Requested IP 和 Server Identifier。"我选了这个 IP，是这个服务器给的。" 其他收到 REQUEST 的服务器看到 Server Identifier 不是自己，默默回收这个 IP。

服务器收到 REQUEST，检查 IP 确实是自己分配的、租约没过期、没被别人占用。都 OK → ACK。ACK 里包含所有网络参数。客户端收到 ACK，正式配置 IP。

当租约过半时，客户端用单播 REQUEST 续租。服务器同意续租 → ACK；IP 已被回收 → NAK。客户端收到 NAK 必须释放 IP 重新从 DISCOVER 开始——这通常发生在服务器重启后。

## 五

下一篇把 IP 池、租约管理和"在 NDIS 层直接发送 DHCP 响应"讲完。特别是最后一点——为什么 DHCP 响应不能用普通的 UDP socket 发？因为客户端此时 IP 地址还是 0.0.0.0，socket API 不知道往哪发。
