# 第12篇：自己动手实现 DHCP（下）—— IP 池、租约与 MAC 绑定

## 一

分配 IP 这件事，本质上是在管理稀缺资源。跟分房子、分车位、分春运火车票是同一个道理——你得有一个公平规则，还得防止有人占了坑不用。

假设你开了一家小旅馆，有 100 个房间。客人来了，你给他一个房间号。客人走了，房间空出来。你还希望老顾客每次来都住同一个房间——这样他放在房间里的东西不会丢。DHCP 服务器的 IP 管理就是这家旅馆的翻版。

## 二

IP 地址池的设计简单到令人发指——一个从 100 到 200 的线性范围。取网关 IP 的前 24 位（子网前缀），后面拼上 100~200。如果网关是 `192.168.137.1`，池子就是 `192.168.137.100` 到 `192.168.137.200`。

为什么从 100 开始而不是从 2？因为 1 是网关自己，2~99 留给将来可能的静态分配——NAS 固定 `192.168.137.10`，打印机固定 `192.168.137.11`。DHCP 动态分配的 IP 从 100 开始，跟静态 IP 互不干扰。一个简单的约定，省去了一套复杂的"IP 冲突检测"机制。

## 三

MAC 地址绑定的意义超出了"欢迎水果"。它直接影响 NAT 映射表的稳定性。

假设手机第一次连 WiFi 拿到 `192.168.137.101`。NAT 表里存着：`101:45678 → google.com:443`。如果手机断开 WiFi 重连，DHCP 给了它一个新的 IP `192.168.137.102`——NAT 表里所有关于 `101` 的映射全废了。虽然旧映射最终会被超时清理，但在清理之前，手机上的应用看到的是连接断开、超时、报错。

所以 `allocate_ip_locked()` 的逻辑是：**先查这个 MAC 之前拿过哪个 IP → 没过期就直接复用 → 过期了才分配新的。** 这是对 NAT 最友好的分配策略。

## 四

租约用 `steady_clock` 计时而不是 `system_clock`。因为租约是相对时间（"从现在起 24 小时后过期"），不需要考虑用户手动改系统时间或者 NTP 同步造成的跳变。`system_clock` 可能因为时间同步突然往前跳一小时——你的 DHCP 租约瞬间过期了一大半。`steady_clock` 是单调递增的，谁也不能让它倒退。

过期租约的清理是 O(N) 遍历——遍历 `leases_` 表，删掉所有 `expires < now()` 的条目。因为 DHCP 客户端最多 100 个，这个复杂度完全可接受。不需要什么精妙的失效队列或定时器轮盘。

## 五

DHCP 响应不能通过普通的 UDP socket 发送。客户端在收到 OFFER 时 IP 地址还是 0.0.0.0。你调用 `sendto()` 往一个全零 IP 发包——操作系统不知道往哪发这个包。

正确的做法是**在 NDIS 层直接构造完整的以太网帧**。目标 MAC 填客户端 MAC（从 DHCP 请求的 `chaddr` 提取，它在链路层已经可达了），EtherType=0x0800，IP 头填服务器 IP 和广播地址 255.255.255.255，UDP 头填 67→68，payload 是构造好的 DHCP 响应。

所谓的"UDP 广播 + MAC 单播"——IP 层是广播（因为客户端还没 IP），链路层是精确送达（因为 MAC 地址是已知的）。这是 DHCP 协议标准允许的——也是局域网里唯一靠谱的做法。

## 六

写 DHCP 服务器——总结起来就是五件事。解析协议头（提取 xid、MAC、消息类型）、管理 IP 池（分配、回收、绑定 MAC）、管理租约（创建、续期、过期清理）、构造响应包（把所有 Option 填对）、在正确的层发送（NDIS 层，不是 socket）。

做好了这五件事，你的设备就能自动拿到 IP 了。但拿 IP 只是第一步。下一篇——把流量从内网 IP 发到公网去——NAT，网络地址转换。
