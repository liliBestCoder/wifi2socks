# 第26篇：IOCP —— Windows 上最快的网络 I/O 模型

## 一

网络编程的 I/O 模型进化史，就是一部"CPU 不想等网卡"的斗争史。

第一代阻塞 I/O——一个线程等一个 socket，1000 个连接要 1000 个线程，每个线程吃 1MB 栈空间，光线程就吃 1GB。第二代 select/poll——一个线程等 1000 个 socket，但每次调用都要把 1000 个 socket 从用户态拷到内核态再拷回来。第三代 epoll/kqueue/IOCP——事件驱动，"有事件了才通知我"，不需要反复拷贝。

但 IOCP 比 epoll 多走了一步。epoll 是"就绪通知"——"这个 socket 可读了，你来读吧"，你还要自己调一次 `recv()`。IOCP 是"完成通知"——你提前投递了 `WSARecv`，内核直接帮你把数据读到 buffer 里，完成时通知你"数据好了"。省了一次系统调用。这就像你提前跟餐厅说"每半小时给我送一杯咖啡"，咖啡到的时候通知你——你不需要每次想喝咖啡都下楼一趟。

## 二

IOCP 的核心三板斧：`CreateIoCompletionPort`（创建完成端口——所有完成通知都送到这里）、异步操作（`WSARecv`/`WSASend`/`ConnectEx`——每个操作附带一个 OVERLAPPED 作为"回执"）、`GetQueuedCompletionStatus`（worker 线程在这里等通知——哪个 socket、什么操作完成了、传了多少字节）。

Worker 线程数等于 CPU 核心数。IOCP 的调度是"当有完成通知且有空闲线程时唤醒一个"。线程多于核心→多余的线程总在等时间片→浪费。线程少于核心→有核心空闲→也浪费。核心数不多不少。

## 三

跟 epoll 坦诚对比：高吞吐量场景（大文件传输、视频流）IOCP 确实快，因为省了 recv/send 系统调用。海量短连接场景（每秒几千个 HTTP 请求，每个几 KB）差距很小——瓶颈在业务逻辑，不在 I/O 模型。IOCP 唯一的致命缺点是**不可移植**——只在 Windows 上存在。Linux 移植需要全部重写成 epoll。
