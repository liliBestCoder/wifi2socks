# 第27篇：无锁队列、Cache Line 与 False Sharing

## 一

多线程编程最难的不是"能跑"，是"跑得快"。加锁就能跑——但要跑得快，你得理解 CPU 缓存怎么工作、原子操作有什么开销、以及一个叫 False Sharing 的隐形杀手。

## 二

SPSC Ring Buffer（单生产者单消费者环形队列）是 reader thread 和 worker thread 之间的通道。两个关键设计让它"无锁"：只有 reader thread 写 `head`，只有 worker thread 写 `tail`。不存在两个线程同时写同一个变量——所以不需要锁，只需要原子操作保证内存可见性。

`acquire`/`release` 语义保证了正确的内存顺序。生产者写完数据后用 `release` 更新 head——这之前的所有写操作不会被重排到之后。消费者用 `acquire` 读 head——这之后的所有读操作不会被重排到之前。保证了消费者看到的 head 值对应的数据已经完整写入。

批量操作进一步摊薄了原子操作成本——一次入队 256 个包，只需要 2 次原子操作（开始前读 tail，结束后写 head）而不是 256 次。

## 三

False Sharing 是多核性能最阴险的杀手。如果 `head` 和 `tail` 在同一个 64 字节 cache line 上，生产者写 `head` 会让消费者所在核心的这个 cache line 全部失效。消费者读 `tail` 就变成 cache miss——要等 100 个 CPU 周期从内存或共享缓存重新加载。即使 `head` 和 `tail` 是完全独立的变量，它们因为"同居"在一个 cache line 上而被误伤。

消除方法：`alignas(64)` 强制每个变量独占一条 cache line，中间用 `char _pad[64]` 隔开。一个没有运行时成本的修饰符，换来了 40% 的吞吐量提升——在没有加 `alignas(64)` 的最初版本里，8 个 worker 的吞吐量只有加了之后的约 60%。

## 四

PacketPool 预分配 32768 个 `INTERMEDIATE_BUFFER`，用完放回池中循环使用。没有 `new`/`delete` 的碎片和系统调用开销。32768 = 512（一次 IOCTL 的批量大小）× 8（worker 数量）× 8（每个 worker 可能持有的批次数）。这个大小保证极端流量下也不会耗光。如果耗光——丢弃新包比动态分配更优，因为动态分配可能带来不可预测的延迟抖动。
