# 第5篇：第一次偷包 —— 绑卡与抓包实战

## 一

第一次从 NDIS 驱动里读到一个真实数据包的时候，我已经在电脑前坐了七个小时。驱动装好了，适配器枚举成功了，Tunnel 模式也设好了，IOCTL 发出去了——返回的 buffer 全是零。搞了半天，发现是 `ETH_M_REQUEST` 的大小算错了，`EthPacket` 数组的起始地址偏移了 8 个字节。修正之后，buffer 里终于出现了数字。

我盯着那一串十六进制看了好几分钟。`45 00 00 3c 1c 46 40 00 40 06 ...`——这是某个程序发出的 TCP SYN 包。它刚刚从网卡上被抓下来，还没到达 TCP/IP 协议栈，就被我截获了。这个包本来应该在几微秒之后被 Windows 的内核拆解、路由、转发，但它永远不会到了。它被我拦截了。

这种感觉很难描述。如果硬要说，有点像你第一次撬开了自己手机的後盖，看到了里面的电池和电路板。你什么都没弄坏，但你知道了那些看不见的地方长什么样。

程序员的快乐大多是这样——不是创造了一个新东西，而是看到了一个旧东西的内部。

## 二

动手之前，有三件事必须做对。少一件，后面的全白费。

**第一步：确认驱动在运行。** WinPkFilter SDK 的 `CNdisApi` 封装了这个过程。底层就是用 `CreateFile` 打开 `\\.\NDISRD` 这个设备文件——能打开就说明驱动在跑。如果打不开，大概率是驱动没安装、没签名被拦截、或者装了不兼容的老版本。这一步不过，后面的都别想。

**第二步：找到正确的网卡。** 你的 Windows 电脑上可能有很多"网卡"——物理网卡、WiFi 网卡、蓝牙虚拟网卡、Hyper-V 虚拟交换机、VirtualBox Host-Only、WSL 虚拟网卡、各种 VPN 的 TAP 适配器……真正要绑的是哪一个？WiFi 模式下找 WiFi Direct 虚拟适配器，有线模式下找物理以太网适配器。选错了就相当于在错误的电话线上窃听——你能听到声音，但不是你想听的那个。

**第三步：设置 Tunnel 模式。** 这一步决定了你是"旁观"还是"劫持"。WinPkFilter 支持多种模式：Listen 模式只是"复制一份给你看，原包继续走"；Tunnel 模式是"原包不走了，你来决定它的命运"。透明代理必须用 Tunnel，因为我们不能让 TCP SYN 包到达 Windows 协议栈——Windows 会发现目标端口没人监听，回一个 RST，连接就死了。

```cpp
ADAPTER_MODE mode;
mode.hAdapterHandle = adapter_handle;
mode.dwFlags = MSTCP_FLAG_SENT_TUNNEL | MSTCP_FLAG_RECV_TUNNEL;
// 这两个 flag 的意思是：进来的和出去的，都归我管
```

设好之后，Windows 的协议栈就跟这个网卡"断开"了——不再直接处理这个网卡的包。接管生效。

## 三

包被拦截了，堆在内核态的队列里。怎么取出来？批量读。

WinPkFilter 提供了 `IOCTL_NDISRD_READ_PACKETS`。核心思路是一次 IOCTL 请求几百个包，而不是一个一个取。为了做到这一点，需要准备好：
- 几百个空 `INTERMEDIATE_BUFFER`（从 PacketPool 里拿）
- 一个 `ETH_M_REQUEST` 结构体（变长的，手动 malloc）
- 一次 `DeviceIoControl` 调用

返回时，`dwPacketsSuccess` 告诉你实际读到了几个包。可能是 0（网络空闲），可能是 10、50、200、512。流量大时一次能读到几百个，流量小时可能连续十几次 IOCTL 都返回 0——都是正常的。

真正的 reader loop 跑在一个独立线程里，只做一件事：尽快把包从内核态捞出来，按 hash 分发到不同的 worker queue。不在 reader thread 里处理包，因为处理一个包可能要 DNS 查询、GeoIP 查表、SOCKS5 握手，都是耗时操作。reader 的职责是"最快速度清空内核队列"，工人的职责是"仔细处理"，这是典型的生产者-消费者分离。

## 四

处理完的包有两种命运。一是被消费了（我们处理了，比如 TCP SYN 被我们重定向到了本地端口），二是被透传（比如 ARP 包我们不管，原样放行）。

放回去有两个方向。

`send_to_mstcp`：假装这个包是从网线上正常收到的。用于我们构造的响应包——比如 DHCP OFFER、DNS 响应——需要让目标设备收到。

`send_to_adapter`：假装这个包是协议栈正常发出的。用于我们主动发起的请求——比如我们自己想做一次 DNS 查询。

用错方向的结果很惨。比如 DHCP OFFER 如果用 `send_to_adapter` 发——它会被当成"我们主动发出的上行包"，发到公网上去。而手机在一个局域网里，永远等不到这个 OFFER。

## 五

现在我们真的读到了第一个包。`INTERMEDIATE_BUFFER` 的 `m_IBuffer` 大概是这样的：

```
ff ff ff ff ff ff 12 34 56 78 9a bc 08 06 00 01
08 00 06 04 00 01 12 34 56 78 9a bc c0 a8 89 01
00 00 00 00 00 00 c0 a8 89 64
```

四十几个字节，翻译成人话："谁的 IP 是 192.168.137.100？告诉我你的 MAC 地址。"——这是一个 ARP 请求。

第一个 `ff ff ff ff ff ff` 是全 F 广播 MAC（发给所有人）。`12 34 56 78 9a bc` 是发送者的 MAC。`08 06` 是 EtherType——ARP。后面的 ARP 载荷里：`c0 a8 89 01` = 192.168.137.1（发送者 IP），`c0 a8 89 64` = 192.168.137.100（目标 IP，在问"你是谁"）。

一个 TCP SYN 包就更长也更复杂——以太网头 14 字节 + IP 头 20 字节 + TCP 头 20 字节起，加起来最少 54 字节。每一个字段——TTL、窗口大小、序列号——都有人在三十年前定义好了它的含义。

这些字段后面会细讲。下一篇——以太网帧解剖课。
